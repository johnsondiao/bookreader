# 音频包格式规范（Audio Package Format）

> 版本：v1.0 · 制定日期：2026-09-30 · 最后修订：2026-09-30
> 适用范围：PC 端合成工作台导出 → 手机端「朗阅」导入播放
> 配套设计：docs/audio-synthesis-split-plan.md
> 本版要点：每章单文件 + 句级偏移、注释独立段与 `noteRef` 跳播、**支持部分章节包与逐章合并**、正文/注释音色定案（女声念正文 / 男声念注释）
> **合成引擎已定案：腾讯云「实时语音合成」`TextToStreamAudioWS`**（单次 **600 汉字**，WebSocket；2026-09-30 核实官方文档后选定，详见拆分计划 §九.6.1）。该接口一次返回**整批连续 PCM 音频 + 字级毫秒时间戳**，故采用**批级合成**：把连续句子打成 ≤600 字的批，批内句间停顿由引擎自然生成（不用我们插固定静音）、句子边界由时间戳精确给出，只有**批与批之间**才需要 PCM 拼接 + 偏移平移。备选方案（腾讯云基础接口 150 字 / MiniMax / 讯飞）**产出的包格式完全一致**，仅 PC 端偏移算法不同，手机端播放器零改动。

---

## 一、设计目标

1. **自带源文件**：音频包内包含原始电子书（TXT/EPUB），手机端导入即可阅读+听书，无需再从别处传书。
2. **句子级对齐**：音频以「章节 + 每句偏移」组织，播放器可把当前朗读位置精确对齐到文本并高亮该句。
3. **无缝连续播放**：每章导出**一个** mp3（PC 端逐句合成后 **PCM 无损拼接**再统一转码，无接缝、无爆音），避免逐句文件的爆音与卡顿。
4. **断点可恢复**：靠 manifest + 文件名即可重建索引，不依赖外部数据库。
5. **增量导入 + 逐章合并**：一个包允许**只含部分章节**的音频；同一本书可分多次导出多个包，手机端按 `(bookId, chapterId)` **逐章合并**入库，重复导入不产生重复文件，已存在章节默认跳过。

## 二、文件结构（zip 包）

```
{bookTitle}.langyue.zip
├── manifest.json              # 包的唯一索引与对齐契约（详见第三节）
├── book/
│   └── source.epub            # 原始电子书（保留原扩展名 .txt / .epub）
├── cover.png                  # 可选：封面图
└── audio/                      # 仅含【本包已合成】的章节（可全书，也可为任意章节子集）
    ├── ch-0.mp3               # 第 ch-0 章（整章已无缝合并）
    ├── ch-1.mp3
    └── ...
```

**命名规则**
- 音频文件：`audio/{chapterId}.mp3`，`chapterId` 与手机端解析器产出的 `ch-N` 完全一致。
- 每章一个文件（不再按句拆文件），句子位置由 manifest 中的 `startMs/endMs` 表达。
- **`audio/` 只包含本包已合成的章节**：一个包可以是全书（`package.mode:"full"`），也可以是任意章节子集（`partial`）——例如只合成到第 10 章，或只补合成第 12 章。缺的章节由手机端从源文件解析目录后标记为「暂无音频」。
- 关键约束：包内 **章节 ID、句子切分、注释（脚注）检测** 必须与手机端 `src/utils/chapterParser.ts` 的 `parseChapters` + `splitSentences` + `isNoteParagraph` **逐字节一致**（含注释标记①/`[1]`/`*` 的识别与「标记↔注释」配对规则）。PC 端务必复用同一份解析代码（建议抽成共享模块或锁版本），否则导入后「跳转到某句/某注释」会错位。

> **偏移计算：批级合成 + 批内字级时间戳（合成引擎定案：腾讯云「实时语音合成」`TextToStreamAudioWS`，单次 600 汉字）**
>
> 腾讯云实时语音合成接口**一次最多 600 汉字**，且**同时返回连续 PCM 音频 + 字级毫秒时间戳**。因此**不再逐句合成，改为「批（batch）级合成」**：把若干连续句子打成 ≤600 字的批，一次提交。
>
> **这个选择带来的三个好处**：
> 1. **批内句间停顿是引擎自然的** —— 整批文本交给引擎连续合成，句与句之间的停顿由引擎韵律模型决定，**不再需要我们插 150ms 固定静音**（彻底消掉"句尾标点自带静音 + 固定 gap 叠加过长"的调参问题）。
> 2. **批内句子边界直接由时间戳给出** —— 不用 PCM 计时切句，精度来自引擎。
> 3. **请求数大幅下降** —— 200 万字的书：600 字/批 ≈ **3,600 次请求**（对比 150 字接口逐句 ≈ 1.5 万次）。
>
> **PC 端合成与偏移计算流程（每章）**：
> 1. **分批**：把本章正文按 `splitSentences` 切句后，**按顺序累积句子成批**，使每批 ≤600 汉字（批边界**必须对齐句子边界**，不切断句子）。单句 >600 汉字的极端长句，按标点**二次切分**成子句（PC/手机共用切分规则）。
> 2. **批级合成**：每批一次 WebSocket 会话 —— `wss://tts.cloud.tencent.com/stream_ws?{参数}`，`Action=TextToStreamAudioWS`，参数 `Codec:pcm`、`SampleRate:16000`、`EnableSubtitle:true`、`VoiceType`=新闻女声/男声、`Speed`、`EmotionCategory`（可选 `news`）。鉴权 HMAC-SHA1：参数字典序拼接 → `GETtts.cloud.tencent.com/stream_ws?{参数}` → HMAC-SHA1(SecretKey) → base64 → **urlencode（必须编码 `+`/`=`）**。
>    - **推荐直接用官方 Go SDK**：`github.com/TencentCloud/tencentcloud-speech-sdk-go`（示例 `examples/ttsexample/ttswsexample.go`），无需手写 WebSocket client。
> 3. **接收响应**：
>    - **binary 帧**：原始 PCM 二进制，累积拼接得到本批完整音频。
>    - **text 帧**：JSON，含 `code`/`message`/`session_id`/`final`/`result.subtitles`。**`subtitles` 分批多次返回，需累积全部**。`final:1` 表示合成结束，**客户端须主动关闭连接**。
>    - `subtitles[]` 每项：`{Text, BeginTime, EndTime, BeginIndex, EndIndex, Phoneme}`；`BeginTime/EndTime` = **该字在本批音频流中的起止（毫秒）**，`BeginIndex/EndIndex` = **该字在本批文本中的字符索引（从 0 开始）**。
> 4. **批内切句**：按 `BeginIndex/EndIndex` 把字级时间戳映射到**我们自己的句子边界** —— 句 `start` = 该句首字 `BeginTime`，句 `end` = 该句末字 `EndTime`（**只用时间戳，不依赖引擎的句级切分**）。
> 5. **批间拼接**：批的 PCM 首尾相接，**批间插入固定静音**（默认 150ms，可配置；PCM 静音 = 全零字节）。后批所有时间戳**整体平移** `+ 前面各批（时长 + gap）之和`。
>    - 批时长 = PCM 字节数 ÷ 32000 × 1000 ms（16kHz × 16bit × 单声道 = 32000 字节/秒），精确到采样点；也可用本批末字 `EndTime` + 尾静音估算，二者互校。
> 6. **写入 manifest**：`sentence[i].startMs/endMs` = 句边界（含句首尾静音，用于播放定位）；`voiceStartMs/voiceEndMs` = 时间戳给出的真实语音起止（用于高亮，跳过静音）。
> 7. 整章 PCM 拼接完成后 → ffmpeg 统一转码 mp3（**CBR**）打包。
>
> **为什么 PCM 而不是 mp3**：mp3 每文件有编码器延迟（首尾各 ~20-50ms 静音），逐批 mp3 拼接会累积接缝；**PCM 是原始波形，字节级可算、拼接零损耗**，最后一次性转 mp3 则只有一次编解码损失。
>
> **时间戳与 PCM 互校**：若「PCM 算出的批时长」与「本批末字 `EndTime` + 尾静音」偏差过大，说明该批异常（静音异常长/合成截断），PC 端应告警。
>
> **断点续合 / 重试（批级）**：每批 PCM 单独落盘（工作缓存，不进包）+ SQLite 记录**批级**状态；中断后从第一个未完成批继续；某批失败只重试该批，**已成功批不重复合成、不重复扣费**。批级粒度（约 10~20 句）是请求效率与续合粒度的最佳平衡。
>
> **停顿调优**：`SegmentRate`（断句敏感阈值 0/1/2，默认 0，值越大越不易断句）可微调句间停顿；`Speed` [-2,6] 调节语速。批**内**停顿由引擎决定，批**间** gap 才是我们控制的（默认 150ms）——**建议批边界尽量落在段落/语义大停顿处**，让批间 gap 与句间停顿听感接近。
>
> **并发与限流**：精品音色默认 **20 路并发**（错误码 `10002` 并发超限），建议限 8~16 路。错误码：`10001` 参数不合法、`10003` 鉴权失败、`20001/20002/20003` 后台合成失败/超时。
>
> **seek 精度与切句播放**：章节 mp3 由 PCM 统一转码，**必须 CBR（恒定码率）**——手机端 `src/utils/chapterChunks.ts` 靠「帧长固定」把毫秒换算成字节，用来把每一句单独切出来播（第 i 句 = `[本句 startMs, 下一段 startMs)` 那块字节）。所以 **不要用 VBR / CRF 转码**（首帧帧长会带出全章帧长，整章时间轴会整体偏 20%+）。
> 另外 **首帧可能与全章帧长不同**（实测真包首帧 180 字节 / 其余十万余帧全是 144 字节），手机端已做「等距走到底不断链」的帧长校验 + manifest 时长反推兜底。
>
> **计费口径**：腾讯云**汉字、字母、数字、标点、特殊符号、空格、回车各计 1 字符**（1 汉字 = 1 字符）；精品音色后付费 **¥0.3/万字符（不区分梯度）**，**基础/精品音色免费额度 800 万字符**（领取后 3 个月有效、一账号一次）。本项目 200 万字的书在免费额度内 → 支出 ¥0。
>
> ---
>
> **备选方案（若实时接口音色试听不达标）**
> - **A. 腾讯云基础语音合成 `TextToVoice`**（HTTP，单次 **150 汉字**）：同样支持 `Codec:pcm` + `EnableSubtitle` 字级时间戳 + 免费额度，但要退回**逐句/小批合成**、句间需插固定静音。HTTP 更简单，官方 Go SDK（`tencentcloud-sdk-go/tts/v20190823`）现成。**最省事的下位替代。**
> - **B. MiniMax turbo**：HTTP `t2a_v2` + `subtitle_enable/subtitle_type:"word"`，响应返回 `data.subtitle_file`（**JSON 下载链接，需二次下载有时效**）→ 字级毫秒时间戳；按章一次合成、天然无缝；单请求 1 万字符；1 汉字 = 2 字符（¥2/万字符 → 200 万字 ≈ ¥840）。
> - **C. 讯飞超拟人**：**无时间戳** → 退回纯 PCM 计时（逐句合成 + 字节计时 + 偏移累加）；WebSocket 接口；预付费 ¥1000 起。
> - ❌ **长文本语音合成 `CreateTtsTask`**（10 万字符）：**不支持免费额度**，且精品音色 **2.0~2.8 元/万字符**（通用接口的 7~9 倍）→ **不采用**。
>
> **所有方案产出完全相同的包结构与 manifest**，差异只在 PC 端「怎么算出 `startMs/endMs`」，**手机端播放器代码零改动**。
>
> **注释（脚注）的处理**：原文正文里的注释标记（①、`[1]`、`*` 等）与注释正文通常分离（注释在章末或「注释」段）。PC 端：
> 1. 合成**正文**：分批合成去掉注释正文、并**去掉标记 glyph**（避免被念出）的文本，得到本章**前半段（正文段）**；含标记的句子在 manifest 里带 `noteRef`（指向注释 id），`text` 仍保留标记供 UI 展示。
> 2. 把**全部注释**用 `noteVoice`（**与正文音色不同**）分批合成、拼接为**注释段**，追加到本章音频的**后面**，得到 `notes[]` 各自 `startMs/endMs`（偏移位于正文之后）。
> 3. 播放器把整章当连续音轨播（标题 → 正文 → 注释），注释按物理顺序连读；正文遇到 `noteRef` 时在屏幕上对应高亮，想立刻听到该注释可点注释角标手动跳播。
> 这样注释音频"对应序号、位于后面、按需跳转"，正文朗读不被注释打断，且朗读全程零 seek。

## 三、manifest.json 结构

```jsonc
{
  "format": "langyue-audiobook",   // 固定标识，校验包类型
  "version": 1,                    // 格式主版本，不兼容时+1
  "generator": "pc-tts",           // 生成端标识
  "createdAt": "2026-09-30T12:00:00Z",

  "package": {                     // 本包覆盖范围：支持只含部分章节
    "mode": "partial",             // "full" 全书 | "partial" 部分章节
    "chapterIds": ["ch-0", "ch-1"],// 本包实际含音频的章节（= chapters[].id）
    "sourceChapterCount": 32,      // 源电子书总章节数，便于手机端显示「已合成 x / 32」
    "batch": 1                     // 可选：同一本书多次导出的批次号（第 1 批 / 第 2 批 …）
  },

  "book": {
    "id": "b-8f3a...",             // UUID，作为导入后手机库的 bookId（幂等键）
    "title": "湖南农民运动考察报告",
    "author": "毛泽东",            // 可选
    "sourceFile": "book/source.epub",
    "sourceFormat": "epub",        // "epub" | "txt"
    "voice": {                     // 正文音色（定案：新闻女声）
      "key": "tencent-zhiyan-news-female",
      "label": "智燕 · 新闻女声",
      "voiceId": 101011,               // 腾讯云 VoiceType（精品音色）
      "engine": "tencent-tts",
      "params": { "speed": 0, "sampleRate": 16000, "codec": "pcm" }
    },
    "noteVoice": {                 // 注释音色（定案：新闻男声，必须与正文不同）
      "key": "tencent-zhihui-news-male",
      "label": "智辉 · 新闻男声",
      "voiceId": 101013
    }
  },

  "chapters": [                    // 只列出【本包带音频】的章节；未合成章节不出现（手机端从源文件解析完整目录）
    {
      "id": "ch-0",                // 与 audio/{id}.mp3 一致
      "title": "湖南农民运动考察报告",
      "titleStartMs": 0,           // 【新增 v1.1】章标题语音在整章 mp3 里的起点（=0）
      "titleEndMs": 1600,          // 【新增 v1.1】章标题语音结束点；整章开头一段就是标题，念完接正文
      "durationMs": 5300,          // 正文时长（= 末句 endMs），进度条以此为准
      "sentenceCount": 3,          // 必须等于 sentences 数组长度（仅正文句）
      "sentences": [              // 正文句子，下标 = 句子序号；startMs/endMs = 在【正文段】中的偏移
        { "index": 0, "text": "农民运动的兴起是一个极大的问题①。", "kind": "text", "startMs": 0,    "endMs": 1820, "voiceStartMs": 250, "voiceEndMs": 1560, "noteRef": ["n0"] },
        { "index": 1, "text": "……", "kind": "text", "startMs": 1820, "endMs": 3920, "voiceStartMs": 2070, "voiceEndMs": 3650 },
        { "index": 2, "text": "……", "kind": "text", "startMs": 3920, "endMs": 5300, "voiceStartMs": 4170, "voiceEndMs": 5020 }
      ],
      "notes": [                  // 注释（脚注）：独立数组，按 index 排序；音频位于本章【注释段】（正文之后）
        { "id": "n0", "index": 0, "kind": "note", "text": "① 见《湖南农民运动考察报告》原注……", "startMs": 5400, "endMs": 7000, "voiceStartMs": 5400, "voiceEndMs": 6850 }
      ],
      "notesDurationMs": 7000     // 含注释段的整章文件时长（≥ durationMs）
    }
    // ... 本包其余【已合成】章节
  ],

  "integrity": {
    "chapterCount": 2,             // 【本包】带音频的章节数（= chapters.length；partial 包即其子集）
    "sentenceCount": 10860,        // 【本包】正文句数合计（不含注释）
    "noteCount": 420,              // 【本包】注释条数合计
    "totalBytes": 123456789,
    "sourceHash": "sha256:..."     // 源文件校验，导入时比对（不匹配仅告警，不阻断）
  }
}
```

**字段说明**
- `package`：本包覆盖面。`mode:"partial"` 表示**只含部分章节**（`chapters[]` 即本包章节清单）；`chapterIds` 必须与 `chapters[].id` 一致；`sourceChapterCount` 供手机端显示「已合成 x / N 章」；`batch` 用于区分同书多次导出。
- `book.voice` / `book.noteVoice`：正文音色与注释音色，**两者必须不同**。**定案（引擎＝腾讯云通用语音合成·精品音色）：正文用新闻女声（`VoiceType` 101011 智燕 / 101012 智丹 / 101022 智虹 三选一），注释用新闻男声（101013 智辉 / 101014 智宁 / 101020 智刚 / 101021 智瑞 四选一）**。`voiceId` 即腾讯云 `VoiceType`；音色字段**仅记录用途、播放不依赖**（音频已固化音色），故多个包音色不一致也不阻断合并。
- `sentences[].kind`：`text` 正文 / `note` 注释，沿用手机端 `isNoteParagraph` 判定，便于播放时切换音色、UI 区分。
- `sentences[].startMs/endMs`：该**正文句**在章节 mp3【正文段】中的起止偏移（毫秒）。**对齐核心字段**，由 PC 端「批级合成 + 批内字级时间戳切句 + 批间 PCM 平移」计算得到，句间连续无缝。
- `sentences[].voiceStartMs/voiceEndMs`：**可选**，句内**真实语音**的起止（毫秒），由 API 字级时间戳（`Subtitles` 首字 `BeginTime` / 末字 `EndTime`）精修得到，用于高亮（跳过句首尾静音）；缺省时高亮回退用 `startMs/endMs`。
- `sentences[].noteRef`：可选，字符串数组，指向 `notes[].id`。当该正文句含注释标记（①、`[1]`、`*` 等）时存在；播放器在正文连播经过此句时把对应注释高亮出来，用户点注释角标可跳播该条注释音频（一句可含多个标记 → 数组按顺序播放）。**注意**：注释音频在音频流里整体排在正文之后，所以「注释紧跟被引用句」是 UI/手动跳播实现，不是连播顺序。
- `chapters[].notes[]`：注释（脚注）数组，每项为一条独立注释音频：`id`（如 `n0`）、`index`（序号，从 0）、`kind:"note"`、`text`、`startMs/endMs`（在**注释段**中的偏移，位于正文之后）、`voiceStartMs/voiceEndMs`（**可选**，同句子的语音起止语义：由注释批的字级时间戳精修，缺省时高亮回退用 `startMs/endMs`）。
- `chapters[].titleStartMs` / `titleEndMs`（**可选，v1.1 新增**）：本章标题语音在**整章 mp3** 里的区间。PC 端把章标题单独合成一段、前置到每章音频开头，听感上是「（标题）……正文」，并留 `gap` 静音与正文隔开。**标题不占正文句号**（`sentences[]` 里仍是纯正文，index 不变），只是整章时间轴向后平移，手机端按 `startMs` 定位即可自动对齐。缺这两个字段（=0）表示**本章不朗读标题**（旧包兼容），手机端仍按正文正常播放、标题仅作显示。
- `chapters[].durationMs`：正文时长（= 末句 `endMs`），进度条以此为准。
- `chapters[].notesDurationMs`：含注释段的整章文件总时长（≥ `durationMs`）。
- `integrity.chapterCount` / `sentenceCount` / `noteCount`：均为**本包**口径（不是全书），用于校验包内数据自洽。
- `integrity.sourceHash`：源文件 sha256。导入时比对，**不匹配仅告警、不阻断**（同一本书不同批次可能用不同副本的源文件）。

### 3.1 注释标记 ↔ 注释正文 配对规则

**目标**：把正文里出现的标记（①、`[1]`、`*` 等）和章末/「注释」段里的注释正文一一对应，使 `noteRef` 指向正确的 `notes[].id`。**PC 与手机必须共用同一套规则**（建议在共享解析模块里实现 `pairNotes(chapter)`，复用 `isNoteParagraph`）。

**1) 标记 token（正文侧，按出现顺序扫描）**
识别以下任一为标记，并提取 **key**：
- 带圈数字：①–⑳（`\u2460`–`\u2473`）、㉑+（`\u3251`+）→ key = 数字值；
- 上标数字：¹²³（`\u00B9`/`\u00B2`/`\u00B3` 及 `\u2070`+）→ key = 数字值；
- 方括号/括号数字：`[n]`、`（n）`、`(n)`、`【n】`、`〔n〕`（`n` 为 1–3 位阿拉伯数字）→ key = n；
- 星号/符号：`*`、`＊`、`†`、`‡`（可连续 `**` 表示第 2 个注释）→ key = 出现序数。
按正文阅读顺序给每个标记一个**出现序号**；一句内多个标记按左到右排列。

**2) 注释定义（注释段侧，复用 `isNoteParagraph`）**
注释段 = 本章内被 `isNoteParagraph` 判为 `note` 的段落（不含纯「注释/注解」标题行本身）。从每条注释正文的**开头**提取 key：
- 行首带圈/上标/方括号/括号/编号数字 → 取该数字；
- 行首 `*`/† 等符号 → 取出现序数；
- 无显式 key（纯 bullet 且无数字）→ 用「注释段内出现序数」。

**3) 配对策略（先 key 后 ordinal）**
- **按 key 配对（优先）**：标记与注释都能提取数字 key 时，`标记key == 注释key` 即配对，顺序无关、最稳。
  例：正文 `…问题①。` ↔ 注释段 `① 见原注……` → key 均为 1 → 配对。
- **按 ordinal 配对（兜底）**：key 缺失或冲突（如大量 `*` bullet、纯顺序 ①②③ 且注释段也纯顺序）时，按出现序一一对应：第 i 个正文标记 ↔ 第 i 条注释定义。
- **多标记**：一句内多个标记 → 该句 `noteRef` 为 `[对应注释id, …]`，按左到右顺序。
- **缺失 / 孤儿**：
  - 正文有标记但注释段找不到对应定义 → 仍保留 `noteRef`，但指向的 `notes[].id` 不存在；播放器跳过该标记继续正文，PC 导出时告警「标记 X 无对应注释」。
  - 注释段有定义但正文无标记引用 → 仍合成进 `notes[]`（`noteRef` 为空），可在注释列表查看。

**4) 合成时的文本处理**
- 正文送 TTS 前**去掉标记 glyph**（避免被念出），但 `sentences[].text` 仍保留标记供 UI 展示与 `noteRef` 标注。
- 注释正文送 TTS 时保留其自身编号（如「① 见……」会念「一、见……」），或按需去掉编号只念内容——由 `noteVoice` 设定决定。

**5) 一致性约束**
PC/手机必须复用同一份 `isNoteParagraph` 与本节配对规则；任一边规则改动都需同步另一端并升 `manifest.version`，否则 `noteRef` 指向错注释。

## 四、对齐契约（播放器如何使用）

每章 mp3 的**时间轴三段**：`[0, titleEndMs)` 章标题段 → `[titleEndMs, durationMs)` 正文段（含句间静音）→ `[durationMs, notesDurationMs)` 注释段。章标题不占正文句号，手机端播到章首会先念「本章标题」再进正文。

播放器当前阅读位置用 `(chapterId, sentenceIndex)` 表示，对齐规则：

| 播放动作 | 实现 |
|---------|------|
| 整体策略 | **按句切字节**：把整章 mp3 按帧结构切成「第 i 段 = `[本段 startMs, 下一段 startMs)`」的一块字节，`Blob.slice()` 出来单独喂给 `<audio>`，播完换下一段（见下） |
| 章首朗读标题 | `titleEndMs > titleStartMs > 0` 时，段序列首位是 `title` 段（`titleStartMs`→`titleEndMs`），播到它时触发标题高亮；从中间某句起播时**不插**标题段（避免重念） |
| 定位到某句 | 换一个 objectURL 播放（等价于「换一段音频」，**不是 seek**），零延迟、无重播窗口 |
| 高亮文本 | 由「当前在播第几段」直接决定（段序号变了才回调 onSentence / onNote / onTitle），不读 currentTime 反查 |
| 正文句含注释标记 | **不再自动插播**（插播要「跳回正文」的回退 seek，Android 上必然重念）；改为注释按物理顺序在正文念完后连读，屏幕高亮跟随；想「这里就听到注」时点该句末尾的注释角标 → 切到该注释那段播 |
| 单条注释定位 | 切到 `notes[k].startMs` 那一段（如用户从注释列表点开某条） |
| 连续播放本章 | 段段相接播完（标题 → 正文 → 注释），`ended` 事件收尾并续下一章 |
| 章节跳转 | 切到新章节的段序列从头播 |
| 单句重播 | 重播该句那一段（从这一句的第一帧开始，绝不重念上一句尾巴） |
| 进度条 | 用 `chapters[].durationMs` 显示整章 |

**为什么是「按句切字节」而不是「整章连播 + 进度途中零 seek」**（v1.6.3 定案）： Android WebView 上报的 `currentTime` 是媒体时钟的阶梯值（约 250ms 刷新一次），且**滞后于喇叭里真正在响的位置**一个输出缓冲（约 200~300ms，正好一个汉字）。只要播放器发生过一次 seek（跳句、跳注释），seek 回段首就会把该段开头已念过的 200~300ms 再念一遍 —— 第一版无条件 seek 是「每句重三个字」，改成「位置已在段内就不回退」仍剩「每句重一个字」。
与其绕开 seek，不如**把 seek 从根上删掉**：每次只把「这一句那一块字节」交给播放器，起点就是这一句的第一帧 —— 物理上不存在「多播一遍」的机会。段尾最多多带一帧（36ms，句尾静音），段首必须落在帧边界（否则解码器丢帧）。
**回退**：若某环境解不了 blob 切片（`paused`/`error`/不动），播放器自动退回整章连播，高亮改由 currentTime 反查（老行为），此时才可能出现开头的重复字。


**为什么每章一个文件 + 每句偏移**：PC 端逐句合成 PCM 后无损拼接为整章单文件（天然无缝），每句边界由 PCM 字节数精确计算；整章单文件既无缝又只需极少文件数，导入/扫描/播放都轻。

## 五、手机端导入与逐章合并（概要）

### 5.1 导入流程
1. 用户在「我的」页选 zip → Capacitor Filesystem 解压到临时目录。
2. 校验 `manifest.format` + `version`（`sourceHash` 不匹配仅告警不阻断）；核对 `package.chapterIds` 与 `audio/{id}.mp3` 一一对应、各章 `sentenceCount` 与 `sentences` 长度一致。
3. **源文件**：若 `book.id` 尚未在书架 → 从 `book/source.*` 导入并解析出**完整章节目录**（复用现有 EPUB/TXT 解析）；已存在则跳过，不重复导入。
4. **逐章合并入库**：把本包 `chapters[]` 逐条并入该书的音频索引（音频落 `books/{bookId}/audio/{chapterId}.mp3`，元数据并入 `books/{bookId}/manifest.json`）：
   - 该章**不存在** → 新增；
   - 该章已存在且 `durationMs` 相同 → **跳过**（幂等）；
   - 该章已存在但内容不同（重新合成 / 换音色 / 时长变化）→ **覆盖**并更新（视为「重合成补丁包」）。
5. 合并后本书 `chapters[]` = 历次导入各包章节的**并集**；源目录中未出现在任何包里的章节即「暂无音频」（听书入口置灰，阅读不受影响）。
6. 完成提示：「本次合并 N 章，本书累计 M / `sourceChapterCount` 章有音频」。

### 5.2 逐章合并语义（长书友好）
- **可分次导出、分次导入**：一本 32 章的书，PC 端可先导 `ch-0..9` 的包，日后补 `ch-10..19`、`ch-20..31`；手机端逐包导入自动累加成完整音频库。
- **只需重合成若干章**：PC 端只导出这几章的小包，导入后**只覆盖对应章节**，其余不动（省流量、省时间）。
- **单章包也合法**：每包章节数不限，手机端按章建索引，导入可后台分批进行防卡顿。
- **不要求一次到位**：`package.mode` 为 `partial` 是正常情况，手机端**不因缺章拒绝导入**，缺的章只是「暂无音频」。

## 六、版本兼容与扩展位

- `format`/`version` 不匹配 → 拒绝导入并提示「请升级 App / 重新导出」。
- `package.mode` 为 `partial`（缺章）属正常情况，手机端**不因缺章拒绝导入**；只有 `format`/`version` 不兼容才拒绝。
- `book.id` 相同即视为同一本书，允许跨包合并；`book.id` 不同则视为新书各自入库。
- **v1.1 新增可选字段（向后兼容）**：`chapters[].titleStartMs/titleEndMs`。旧包没有这两个字段 → 手机端按「本章不朗读标题」处理，正文播放完全不受影响；新包给旧 App 也能正常导入（忽略新字段）。因此**不必为了朗读标题而升 `version`**（`version` 仍为 1）。
- **v2 预留**：句子级可扩展 `charStart/charEnd`（在章节正文中的字符区间）支持「句内逐字高亮」；当前 v1 仅句级。
- **逐字高亮（可选 v2）**：若 TTS 后期支持词级时间戳，可在 `sentences[]` 内加 `words:[{text,startMs,endMs}]`，不改文件结构。

## 七、已知权衡

| 取舍 | 说明 |
|------|------|
| 合并质量 | 整章由 PC 端批级合成 PCM 后无损拼接，最后统一转码 mp3（仅一次编解码损失）；批内句间停顿由引擎自然生成，批间插入固定静音（默认 150ms），无爆音无接缝 |
| 单句重播精度 | 用 startMs/endMs 区间循环，HTML5 audio 帧级定位对句级足够；更细的逐字高亮见 v2 |
| 解析一致性 | 必须复用手机端 `splitSentences`，PC/手机解析一致，否则 startMs/endMs 与文本错位 |
| 引擎无关性 | 偏移计算只依赖「批级合成 + 字级时间戳 + PCM 字节计时」；换引擎不影响包格式 |
| 大书体积 | 整章单文件，体积与"整章未拆"相当，远小于逐句方案；无万级小文件开销 |
